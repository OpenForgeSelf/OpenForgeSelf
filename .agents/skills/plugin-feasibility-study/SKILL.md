# 插件可行性研究（立项 · 命名 · 拍板）

本技能是「新建插件」流程的**第一步**，先于 `plugin-development`。
它只解决三件事：**做什么 / 叫什么 / 做多大**。
- 怎么接才合规（契约、事件族、能力供给选型）→ 转派 `architecture-design` 出 ADR
- 怎么落地 → `plugin-development`
- 怎么证明 → `e2e-testing` / `plugin-publish-verify`

---

## 一、什么时候用

- 用户提出一个新插件想法，但需求 / 命名 / 范围还没定稿
- 要把某个宿主内置功能拆成独立插件，需先论证可行性
- 评估「某功能该不该做成插件、做成多大的插件」

**禁止**：跳过立项直接开写代码。
历史教训：AgentHub 曾叫 `CliAgent`（CLI 只是众多交互口之一，命名把职责锁死在实现手段上），
导致职责错位，后来改名重做、浪费一轮。

---

## 二、立项流程（5 步，顺序不可省）

1. **调研（Research）**
   - 行业格局：同类方案怎么做（MCP / ACP / A2A 等协议层；各候选接入形态矩阵）
   - 本仓既有能力：`grep` 代码确认能否复用（如 AIAgent 的工具注册白名单
     `AIAgentService.ResolveOwnToolDefinitions()`，新工具须加白名单才对 agent 可见）
   - 产出 `specs/<NNN>-<slug>/research.md`
2. **可行性报告（Feasibility）**
   - 技术上能不能做、有没有坑（依赖、协议、长连接、热重载、宿主集成 7 处等）
   - 收益 / 成本 / 风险三栏对照
   - 产出 `specs/<NNN>-<slug>/feasibility.md`
3. **设计方案（Design）**
   - 分层架构、数据模型、端点、工具清单、安全模型、分期（P0-P3）、决策清单
   - **必须配流程图**（见 §四 流程图强制清单）
   - 遇「契约放哪层 / 内核接缝」问题 → **转派 `architecture-design` 出 ADR**，不自行裁定
   - 产出 `specs/<NNN>-<slug>/design.md`
4. **命名（Naming）**
   - **必须在功能定稿之后**才命名（不是先起名再凑功能）
   - 过「名实相符三问」（见 §三）
   - 命名结果：目录 / 程序集 PascalCase（如 `AgentHub`）、运行时 id kebab-case（如 `agent-hub`）
5. **决策拍板（Decision）**
   - 把 research / feasibility / design / 命名 汇总，**交用户确认**
   - 用户确认后才转 `plugin-development` 落地
   - 未确认前不写实现代码

---

## 三、名实相符三问（命名铁律）

新插件命名必须逐条通过：

1. **覆盖全部职责段**：名字要能囊括它真正要做的所有事，不留大窟窿
   （如「管理本机其它 agent」不能叫只反映某一种交互口的名字）
2. **不绑死实现手段**：名字反映「做什么」，不反映「用什么技术做」
   （反例 `CliAgent`：CLI 只是众多交互口之一，叫 CliAgent 把职责锁死在命令行）
3. **不撞名**：不与本仓已有插件 / 类 / 概念重名或易混淆

---

## 四、流程图强制清单（设计方案必画）

用户要求「一图胜千言」，设计方案**必须**配以下 5 图（mermaid 或等价），
**每图下方写「画图发现的缺口」**，文末汇总成表：

1. **总体架构图**
2. **主流程时序图**
3. **状态机图**（有状态的对象）
4. **扩展判定树**（新增 X 时怎么走）
5. **数据流 / 降级图**（外部格式漂移 / 失败如何降级）

文末必须有「**图解自查：发现的缺口与处置**」表，把缺口回写 `tasks.md`（T0xx）。

> 实证：032-agent-hub 画图实际查出 8 个原设计无下落的分支（SSE 断线补齐、审批等待是否占执行超时、
> 大文件流式读取、claude cwd 不可逆编码、宿主重启任务回收 `Interrupted`、跨 agent 同 cwd 并发互斥、
> 自身仓库 `dangerousCwd` 禁写、`auth_expired` 分类）——漏画就漏需求。

---

## 五、设计必答扩展性四问

每个设计方案必须回答：

1. **新对象怎么加**：声明式优先（JSON / 配置热加载，不改代码）还是必须写代码？
2. **新能力面怎么加**：用 Facet（能力面）+ 显式降级（未知能力面不崩，给出明确 ❌）建模
3. **契约放哪层**：放 `Abstractions`（跨插件共享）还是插件内私有？首个消费者出现再上移并出 ADR
4. **外部格式漂移怎么发现**：版本号（`profileVersion`）+ 探针断言（`probe`）能否早期暴露不兼容

## 六、技能边界（勿混）

| 阶段 | 负责技能 | 解决 |
|---|---|---|
| 立项（做什么 / 叫什么 / 做多大） | **本技能** `plugin-feasibility-study` | 需求、命名、范围、可行性 |
| 架构（契约 / 事件族 / 能力供给） | `architecture-design` | 出 ADR，定合规接入方式 |
| 开发（怎么落地） | `plugin-development` | 门禁 + e2e + 发布 + 走查 四步闭环 |
| 验证（怎么证明） | `e2e-testing` / `plugin-publish-verify` | 端到端 + 发布热重载 |

---

## 七、完成定义与衔接

- 立项产出（`specs/<NNN>-<slug>/{research,feasibility,design}.md` + 命名 + **用户拍板**）齐活，本技能即完成。
- **下一步**：用户确认后转 `plugin-development`（实现 → 门禁 → e2e → 发布 → 走查）。
- **复盘回写（技能自进化闭环）**：插件做完后，把
  - 新坑事实（踩过的环境 / 协议 / 热重载坑）
  - 模板缺章节（本技能 §四 流程图清单即由此补强）
  - 被推翻的决策（写成规则，而非只记结论）
  写回本技能。
- **新增 / 修改技能必须同步 `AGENTS.md` §2.4**（不在表里 = 后续会话必漏读，历史上因此漏发插件、漏跑 e2e）。
