# 01 分诊与根因（P0 / P2）

## P0 分诊：先查台账，再动手

1. 列出本次任务**触碰区域**（如：插件契约 / 鉴权 / 插件库 / ps1 脚本 / dev 环境 / Agent 委派）。
2. 用区域词查 `docs/11-troubleshooting/problem-classes/README.md` §「按 tags 检索」→ 得到候选 PC 清单。
3. 对每个候选 PC 读 front-matter 的 `invariant` 与 `lens`，判断本次改动是否**受同一不变量约束**。
4. 判定分支：
   - **命中且本次是它的又一次发生** ⇒ 复发 = 逃逸：P0 立即转做 P7 逃逸分析（回答"上次守卫为什么没防住"），再回 P1；
   - **命中但只是相邻区域** ⇒ 把 PC.lens 问题抄进 Spec「Failure Modes」节（规范 v1.2.0 Stage 2），继续正常流程；
   - **未命中** ⇒ 正常修复流程，P2 归类时判断是否值得新建 PC。

⛔ 禁止跳过 P0 直接改代码——历史教训（PC-005）：10-08 AgentHub DI 修复没做同类扫查，10-17 同族缺陷再犯，多花一整批工时补账。

## P2 归类：问题类陈述的写法

**一句话不变量**（必须可判定真假，不要写"要注意 X"）：
- 好：`被其他插件 ctx.Get<T>() 消费的契约，提供方必须 ctx.Register<T>()（或宿主 seed 清单）`
- 坏：`插件间契约要小心注册`（无法扫描、无法断言）

**5 Whys + 第 6 问**：
- Why1..Why5 追到"系统层面为什么会发生"（不变量破坏点为止，不追到"人不细心"为止——那是伪根因）。
- **第 6 问 = 本技能独有**：「为什么现有流程/守卫/文档没让我一开始就写对？」答案四选一（见 `05-escape-analysis.md` 失败模式表）：找不到索引 / 散文读不懂用不上 / 没有 Stage 问这个问题 / 无守卫强制。第 6 问的答案直接决定 P7 上浮动作。

**特征签名**（决定守卫能长什么样，写法见 `02-sweep-playbook.md`）：
- 优先写成**可枚举断言**（"所有 X 必须 Y"，X 能被反射/源码遍历枚举出来）；
- 枚举不出来才写 grep 签名（`glob` + `regex` + `expect`）；
- 两者都不可行 ⇒ 写 `signature: []` 并在 PC §2 说明"待读码定性"（如 PC-004 候选档）。

## 归类决策：新建 PC 还是并入既有 PC？

| 情形 | 处置 |
|---|---|
| 不变量相同、违反方式相同 | 并入既有 PC，`recurrences` + case 追加 |
| 表象相同但不变量不同（如 PC-001 供给方没注册 vs PC-005 消费方解析时机错） | **分开建 PC**，两文件互相 §"相邻但不同"注记 |
| 既有 PC 的守卫没防住本次 | 并入 + 强制逃逸分析 + 守卫升级（等级或覆盖面） |
