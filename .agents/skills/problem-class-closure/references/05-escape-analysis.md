# 05 逃逸分析（P7 前半，二次复发必做）

> 前提认知：**二次复发 = 流程缺陷，不是代码缺陷**。同一段代码错两次，说明"防它"的机制从来没存在过，或者存在但够不着。逃逸分析的对象是机制，不是人。

## 缺口归因表（四种失败模式，逐问打勾）

前案（同 PC 的上一个 case / 上次的散文教训）→ 为什么没防住本次？

| # | 失败模式 | 自检问题 | 本仓实例 |
|---|---|---|---|
| F1 | **找不到**（无索引） | 上次教训写下来了吗？写在哪？下次设计者有没有一个**必然经过的入口**查到它？ | `index.md` 停更 6 行；教训散在六个地方（AGENTS 括号/Part B/坑表/07 报告/index/TODO） |
| F2 | **读不懂用不上**（只有散文） | 记录里有没有可判定的不变量 + 可执行的签名？还是只有"值得固化"这类愿望句？ | 10-10 报告 §10"同类隐患值得固化"——散文，无 TODO id 无守卫 |
| F3 | **没人触发**（没有 Stage 问这个问题） | 流程的哪个 Stage 强制回答"同类在哪"？Spec 模板有没有对应节？ | v1.1.0 之前：没有——Agent 做完全合规也只能记账 |
| F4 | **没人强制**（无守卫） | 违反不变量时，测试/hook/CI 里有没有人会红？ | PC-003 登记规则在 README 但无机器校验 → 两插件同时漏中 |

多数逃逸是组合（上例 F1+F2+F4）。**每项归因必须落到一个基建动作**（见 `06-infra-upgrade.md` 动作表），只写"下次注意"= 分析无效。

## 输出格式（case §8）

```
前案：<case id 或 散文出处 文件:节>
归因：F1/F2/F3/F4（多选，各附一句证据）
上浮动作：
  - <动作1：改哪个模板/Stage/hook/技能，落到哪个文件>（本批已做 / TODO-<id>）
  - ...
守卫升级：<新等级 + 载体>（复发≥2 强制 ≥G2）
```

## 反模式（禁止）

- 把逃逸原因写成"执行者没读 AGENTS"——AGENTS 74KB 时代没人通读，**读不到是索引的责任，不是读者的**；
- 只做归因不出动作——归因表右列必须全部映射到基建变更或带期限 TODO；
- 逃逸时还按首见写 G1——铁律 4：复发最低 G2。
