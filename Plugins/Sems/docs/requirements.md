## 1. Sems 已核实的现状事实

已读文件：`Services/ProjectService.cs`、`Services/RunnerService.cs`、`Services/ProcessMatcher.cs`、`ToolExtensions.cs`。`Controllers/` 只看了文件名（ProjectsController、ProjectCommandsController、RunsController），正文未读。`plugin.json`、`SemsPlugin.cs`、`TODO.md` 为早先读取的摘要。

- 版本 1.1.1，名称「软件工程管理系统」，前端入口 `/sems`，视图 `SemsView`。
- **数据归属**：项目档案与运行命令的数据不属于 Sems，归宿主的 `IProjectRegistry` 接缝。`ProjectService` 每次调用经 `ctx.Get` 重新解析接缝，接缝不可用时返回 503 或空列表（`ProjectService.cs`）。
- **业务落点**：项目与命令的业务操作集中在 `ProjectService`，进程运行集中在 `RunnerService`；对外工具基类注释声明与 HTTP 端点共用同一份服务实现（`ToolExtensions.cs`）。
- **进程管理**：`cmd.exe /c <script>` 在项目根目录启动，`taskkill /T /F` 杀整树，WMI 查询 `Win32_Process` 检测本机进程，`ProcessMatcher` 按路径前缀与项目类型判定归属；会话表在内存，宿主重启后清空（`RunnerService.cs`、`ProcessMatcher.cs`）。
- **对外工具**：13 个 `sems_*` 工具，返回统一封套 `{success,data|error}`；每次执行结束后调用 `RecordUsageAsync` 上报工具名与耗时（上报去向未核实）。
- **删除保护**：项目仍有存活会话时拒绝移除，且不做任何数据变更（`ProjectService.RemoveProject`）。
- **目录浏览**：只读，只列直接子目录，不列文件、不递归（`ProjectService.Browse`）。

## 4. 方案 B：需求规格（开发方式本身 AI 原生的管理平台）

> 本节是对用户 2026-10-26 贴出的方案 B 原文的需求化细化。原文论点是依据；FR（功能需求）与 AC（验收标准）是据论点推导的条目，仍属提案，不代表已实现。原文没给出的数值阈值、技术选型、数据格式，一律记为「待定」并汇入 4.9，不自行假定。

### 4.1 背景与目标

**背景**：Coding Agent 成为主要代码生产者之后，软件开发的瓶颈从「写出代码」转移到「说清意图、供给上下文、验证结果、承担责任」。传统 DevOps 平台管理人提交的代码和流水线；本平台管理 Agent 的工作，包括任务、会话、轨迹、权限与产出。

**目标**：
- G1 产出可信：Agent 的产出经过可审计的验证后才能进入主干。
- G2 可追溯可追责：每个变更能说清由谁、基于什么、在谁授权下产生，并有明确的人类责任人。
- G3 成本可控：Agent 长时间自主运行不会失控消耗预算。
- G4 可度量可改进：用有意义的指标衡量并持续改进 Agent 的工作方式。

### 4.2 范围与非目标

**范围内**：管理 Agent 的工作所需的 14 项要素（4.5）。

**非目标**：
- 不取代人对高风险变更的最终判断（原文：AI 评审不能完全取代人）。
- 不放松生产环境写权限的门控（原文：生产环境写权限必须严格门控）。
- 不以「AI 生成了多少行代码」作为效能指标（原文）。
- 不自研 Coding Agent 本身（推导，待 4.9 的 U1 确认）。

### 4.3 角色与术语

**角色**：
- 规格制定者、评审者、系统设计者：人，原文 B14 所说的工程师角色变化。
- Agent：承担实现、测试、评审、文档等分工的执行者，拥有独立身份。
- 人类责任人：对某个变更负责的人，每个变更必须有（原文 B7）。
- 平台管理员：维护准入清单、策略与阈值的人（推导）。

**术语**：规格指需求、验收标准、约束与任务拆解的结构化记录；上下文资产指规则文件、文档、技能、工具等供给 Agent 的材料；轨迹指 Agent 一次任务中的完整动作与对话记录；沙箱指隔离、可复现的执行环境；门禁指合并前必须通过的自动化检查。

### 4.4 约定

- 编号：Bn 对应原文第 n 部分；Bn-FRm 为需求；Bn-ACm 为验收标准。
- 措辞：「应」表示必须满足；「宜」表示建议满足；「可」表示可选。
- 优先级：P0 为原文落地顺序第一批；P1 为第二批；P2 为最后一批；「未定级」表示原文落地顺序没有排到，4.7 给建议值，待拍板。
- AC 要求：写出输入、动作与可观察结果；验证手段尚未确定的，在条目内标「待定」。
- 「Sems 现状」取值同文首：已有 / 部分 / 未实现 / 未核实。

### 4.5 需求条目

#### B1 意图与规格层（未定级，建议 P1）

**目标**：Agent 知道什么算完成，评审者有客观依据。规格是「源代码的源代码」，需要版本化。

**需求**：
- B1-FR1 应支持以结构化形式记录需求、验收标准、约束与任务拆解。
- B1-FR2 应支持规格与代码变更双向关联：由规格查到关联变更，由变更查到所依据的规格。
- B1-FR3 验收标准应可转化为测试或评测用例，并能标记每条标准是否已有对应用例。
- B1-FR4 规格应版本化，修改留痕。

**验收标准**：
- B1-AC1 给定一条规格，能列出全部关联变更；给定一个变更，能显示所依据的规格及版本。
- B1-AC2 给定含 N 条验收标准的规格，能显示每条标准是否已关联用例。
- B1-AC3 修改规格后，旧版本仍可查看，已有关联变更仍指向其生成时的规格版本。

**依赖**：B7。
Sems 现状：部分（v1.2.0 源码已有、未发布。22 个 sems_* 工具，含规格版本、双向关联与验收标准覆盖。项目卡片内有规格区：`Plugins/Sems/web/src/SpecPanel.vue`，从「规格」进入，不另开菜单。2026-10-30 插件前端 vitest 21 通过，`pnpm build` 成功；`e2e/plugins/sems/sems.spec.ts` 的「规格主链路」1 passed，截图 `ForgeSelf.Web/screenshots/e2e/sems/sems-specs.png`。后端 `.temp/results-sems-b1b/sems-b1b.trx` 为 passed=103 failed=0。dev-stack `http://localhost:7399/sems` 已走查：空标题拦截、创建、追加 v2 仍保留 AC1、回读 v1。同一后端 `:7301` 无令牌访问规格路径为 401，带令牌列表为 200。未纳入本轮：本地发布、`:51888` 复验。证据见 `docs/ai/pilot/2026-10-30-sems-b1-ui/`。）

#### B2 上下文工程管理（P1）

**目标**：把规则、文档、技能、工具作为组织级资产管理，因为 Agent 的表现很大程度取决于它看到了什么。

**需求**：
- B2-FR1 应把仓库说明文件、架构文档、编码规范、领域知识、技能和可用工具（MCP 服务器）登记为上下文资产，有统一清单。
- B2-FR2 规则应按组织、团队、仓库分层继承，下层可覆盖上层；能查看某仓库最终生效的规则及每条的来源层级。
- B2-FR3 每项资产应有版本与最近更新时间；超过新鲜度阈值（阈值待定）的资产应被标记为可能过期。
- B2-FR4 规则变更前应能评估影响范围，即受影响的仓库与团队。

**验收标准**：
- B2-AC1 对某仓库，能显示生效规则集合及每条规则来自哪一层。
- B2-AC2 一项资产超过配置的新鲜度阈值后，清单中出现过期标记。
- B2-AC3 提交规则变更前，能给出受影响仓库清单。

**依赖**：B10（评估规则变更是变好还是变差）。
Sems 现状：未核实

#### B3 Agent 运行时与沙箱（P0）

**目标**：Agent 在隔离、可复现的环境里工作。沙箱既是安全边界，也是 Agent 能自己跑测试、起服务、验证结果的前提。

**需求**：
- B3-FR1 Agent 任务应在标准化开发容器内执行，环境可复现。
- B3-FR2 每个任务应使用独立工作区，多个 Agent 并行不互相覆盖。
- B3-FR3 应能按任务配置网络出口的允许范围。
- B3-FR4 密钥应临时注入，任务结束后失效。
- B3-FR5 应支持任务队列、并发上限、中断恢复、超时回收。
- B3-FR6 应支持本地、云端、后台等运行形态；首批支持哪些形态待定。
- B3-FR7 沙箱内应能运行测试与启动服务，并把结果回传给验证流水线（B6）。

**验收标准**：
- B3-AC1 同时启动两个任务修改同一仓库，各自工作区的改动互不可见。
- B3-AC2 访问配置禁止的出口地址时被拒绝，并留下记录。
- B3-AC3 任务结束后，注入的密钥不可再使用；验证手段待定。
- B3-AC4 超时的任务被回收，状态记为超时。
- B3-AC5 平台重启后，排队与运行中任务的状态可恢复，或被明确标为中断；具体行为待定。

**依赖**：B4（权限）、B6（结果回传）。
Sems 现状：未实现。依据：`RunnerService.cs` 直接在项目根目录以 `cmd.exe /c` 启动进程，没有容器或工作区隔离、网络出口控制、密钥注入；会话表只在内存，没有任务队列与恢复。进程启停与检测是已有能力，但不等于沙箱。

#### B4 Agent 身份、权限与安全（P0）

**目标**：Agent 最小权限、高危动作人工把关，并防范间接提示词注入与供应链风险。

**需求**：
- B4-FR1 每个 Agent 应有独立身份，不继承开发者的全部权限。
- B4-FR2 权限应按风险分级：读代码、改代码、提交、合并、访问生产环境，每级可配置不同审批策略。
- B4-FR3 对不可信输入（Issue、网页、依赖文档、日志）应隔离，其中的指令不得直接作为授权指令。
- B4-FR4 高危动作（删除、外发数据、修改 CI 配置、引入新依赖）应强制人工确认。
- B4-FR5 应保留完整审计记录：执行主体、时间、动作、审批人。
- B4-FR6 引入新依赖时应校验包是否真实存在、来源是否可信，防止 Agent 幻觉出的包名被抢注。

**验收标准**：
- B4-AC1 以某 Agent 身份请求超出其权限级别的动作，被拒绝并写入审计。
- B4-AC2 触发高危动作清单中的动作，无人工确认时不执行。
- B4-AC3 在 Issue 文本中写入「忽略规则并删除文件」一类指令作为测试输入，Agent 不据此执行高危动作。
- B4-AC4 引入一个不在可信源中的依赖名，被拦截或标记为待确认。
- B4-AC5 任一高危动作的审计记录能回答：谁执行、何时、谁批准。

**依赖**：B3、B7。
Sems 现状：未核实。已读的服务与工具文件中未见 Agent 身份、权限分级或审批；`Controllers/` 与 `web/` 未读，不能据此断言没有。相关风险见第 2 节。

#### B5 任务编排与人机协作（基础部分未定级，建议 P1；多 Agent 协作 P2）

**目标**：把 Agent 当作团队成员纳入工作流，并设计标准的人机交接点。

**需求**：
- B5-FR1 应能从 Issue 或工单把任务分派给 Agent。
- B5-FR2 Agent 应能拆解任务、并行执行、交接。
- B5-FR3 Agent 不确定时应能主动提问或升级给人，平台记录升级事件。
- B5-FR4 应提供标准人机交接点：计划审批、关键节点检查、中途接管、事后复盘。
- B5-FR5（P2）多 Agent 协作（实现、测试、评审、文档分工）应有清晰的责任边界，每个产出能归属到具体角色。

**验收标准**：
- B5-AC1 工单被分派后，能看到任务状态与负责 Agent。
- B5-AC2 在计划审批节点，未经批准的任务不进入实现。
- B5-AC3 人中途接管后，Agent 不再继续修改该工作区；具体机制待定。
- B5-AC4 升级给人的事件能在任务记录中查到。

**依赖**：B3、B4。
Sems 现状：未核实。Sems 管理的是项目进程会话，不是 Agent 任务，两者不能混同。

#### B6 验证流水线（P0，整个平台的重心）

**目标**：代码生产成本趋近于零之后，验证成为稀缺资源；用有限的评审精力守住输出可信度。

**需求**：
- B6-FR1 合并前应运行测试、静态分析、类型检查、安全扫描（SAST、SCA、密钥泄露）、许可证检查；任一硬性项失败则禁止合并。
- B6-FR2 对大体量变更应生成意图与实现的对照摘要，并标出高风险改动；AI 评审结论不得取代人的最终判断。
- B6-FR3 应提供行为级证据：预览环境、端到端测试结果、截图或录屏，附在评审界面。
- B6-FR4 应提供覆盖率之外的测试有效性检查（如变异测试），标出可能「自证正确」的测试。
- B6-FR5 变更应按风险分级评审：低风险（文档、样式）可自动合并，高风险（鉴权、支付、数据迁移）必须由指定的资深人员批准；分级规则可配置。

**验收标准**：
- B6-AC1 未通过某硬性门禁的变更，合并被拒绝，并显示失败项。
- B6-AC2 对非低风险变更，即使 AI 评审摘要存在，合并仍需至少一名人的批准。
- B6-AC3 涉及鉴权、支付、数据迁移路径的变更，没有资深人员批准不能合并。
- B6-AC4 一条没有有效断言的测试能被有效性检查标出；具体手段待定。
- B6-AC5 含界面改动的变更，评审界面能看到预览或截图证据。

**依赖**：B3（沙箱内运行）、B1（验收标准来源）。
Sems 现状：未核实

#### B7 溯源与可追责（P0）

**目标**：每个变更能回答由谁、基于什么、在谁授权下产生，并有明确的人类责任人，Agent 不能成为责任的「真空地带」。

**需求**：
- B7-FR1 每处变更应记录：Agent 身份、模型版本、所依据的规格与上下文版本、授权人。
- B7-FR2 上述信息应保存在提交元数据中，或能由提交反查到的记录中。
- B7-FR3 应可按需保留完整 Agent 轨迹；保留期限策略待定。
- B7-FR4 每个变更应有明确的人类责任人；没有责任人的变更不得合并。

**验收标准**：
- B7-AC1 任取一个已合并变更，能查出 Agent、模型版本、规格版本、上下文版本、授权人。
- B7-AC2 未指定责任人的变更，合并被拒绝。
- B7-AC3 对设置了保留的变更，能查看对应轨迹；查看粒度待定。

**依赖**：B1、B2、B4。
Sems 现状：未核实。已读代码中仅见每次工具执行后上报工具名与耗时，未见变更归因字段；上报去向未读。

#### B8 模型与工具治理（未定级，建议 P1）

**目标**：多种 Coding Agent 与多个模型并存时，统一准入、数据策略、账号与计费，避免各团队各自采购、各自配置。

**需求**：
- B8-FR1 应维护 Coding Agent 与模型的准入清单，未准入的不可使用。
- B8-FR2 应统一数据策略：代码是否出域、供应商是否允许留存或训练，可按仓库或数据分级配置。
- B8-FR3 应统一账号与计费。
- B8-FR4 应能按任务类型做模型路由。
- B8-FR5 模型升级前应评估行为变化，评估方法见 B10。

**验收标准**：
- B8-AC1 使用未准入的 Agent 或模型发起任务，被拒绝。
- B8-AC2 对标记为禁止出域的仓库，任务不能调用会使代码出域的模型。
- B8-AC3 任一任务能查到所用模型与计费归属。
- B8-AC4 模型升级为默认之前，必须有评估记录。

**依赖**：B10、B11。
Sems 现状：未核实

#### B9 度量体系（P1）

**目标**：用有意义的指标衡量效果，避免虚荣指标，并识别「局部提速、整体变慢」。

**需求**：
- B9-FR1 应采集四类指标：流动效率（需求到上线周期、PR 创建到合并时间、评审等待时间）；质量结果（变更失败率、回滚率、缺陷逃逸率、返工与代码流失率）；Agent 表现（任务一次成功率、人工介入率、被拒绝的 PR 比例）；成本效率（每个成功合并任务的成本）。
- B9-FR2 成本效率应以每个成功合并任务的成本为主，不以 token 总量为主指标。
- B9-FR3 不得把 AI 生成代码行数作为效能指标展示。
- B9-FR4 应在同一视图并列产出速度与评审等待时间，以便发现评审队列积压。

**验收标准**：
- B9-AC1 能按时间段查询四类指标。
- B9-AC2 成本指标的分子与分母定义明确；「成功合并任务」的判定口径待定。
- B9-AC3 指标视图中不出现 AI 生成行数。
- B9-AC4 产出速度与评审等待时间在同一视图可对照。

**依赖**：B7、B11。
Sems 现状：未核实

#### B10 对开发流程自身的评测（P2）

**目标**：回答「这次对规则、模型、工具集的调整，让 Agent 变好还是变差」，不再凭感觉。

**需求**：
- B10-FR1 应能用历史任务建立回放基准集。
- B10-FR2 修改规则文件、更换模型、调整工具集之后，应能对基准集回放，并与调整前对比。
- B10-FR3 应输出对比结论（变好、变差或无显著差异）及依据指标；判定标准待定。

**验收标准**：
- B10-AC1 对同一基准集，调整前后各有一份结果，可并排查看。
- B10-AC2 未经回放的规则变更被标记为「未评测」；是否阻止发布待定。

**依赖**：B2、B7、B9。
Sems 现状：未核实

#### B11 成本治理（未定级，建议 P1）

**目标**：防止陷入循环的任务耗尽预算，并优化成本。

**需求**：
- B11-FR1 成本应按任务、团队、项目归因。
- B11-FR2 应支持单任务预算上限；超限后的动作（暂停或终止）待定。
- B11-FR3 应支持并发限制。
- B11-FR4 应对异常（如疑似陷入循环）告警。
- B11-FR5（宜）支持缓存、模型分级（简单任务用小模型）、上下文裁剪等优化。

**验收标准**：
- B11-AC1 设置预算上限后，任务消耗达到上限时被中止并记录原因。
- B11-AC2 疑似循环的任务触发告警；判定规则待定。
- B11-AC3 成本报表能按任务、团队、项目三个维度汇总。

**依赖**：B3、B8。
Sems 现状：未核实

#### B12 运维与交付的 AI 化（P2）

**目标**：把 AI 延伸到交付与运行阶段，同时严格门控生产环境的写权限。

**需求**：

- B12-FR2 宜支持变更风险预测、修复建议生成、值班辅助。
- B12-FR3 Agent 对生产环境默认只读；修复动作必须经审批。
- B12-FR4 所有变更应有可回滚路径。

**验收标准**：
- B12-AC1 Agent 在生产环境尝试写操作，无审批时被拒绝。
- B12-AC2 经审批的修复动作，其回滚路径在执行前已登记。
- B12-AC3 诊断与修复建议标明为建议，不自动执行。

**依赖**：B4、B7。

### 4.6 横切非功能需求

- 可审计：Agent 的动作、审批与策略变更全部留痕，记录不可被 Agent 自身修改。
- 人在回路：高危动作必须人工确认；该原则优先于效率目标。
- 可回滚：任何进入主干或生产的变更都有回滚路径。
- 策略驱动：阈值、分级规则、准入清单、数据策略可配置，不写死在代码里。
- 可复现：同一任务在相同输入下的执行环境一致。
- 性能、容量、可用性指标：待定，见 4.9。

### 4.7 优先级与分批

- 第一批（P0）：B6、B3、B4、B7。它们决定能否安全地放手让 Agent 工作。
- 第二批（P1）：B2、B9。它们决定效率提升多少、能否被证明。
- 第三批（P2）：B5 的多 Agent 协作部分、B12、B10。
- 未定级（建议值，待拍板）：B1、B5 基础部分、B8、B11 建议 P1；B13、B14 建议 P2。

**整体骨架**：规格与上下文管「输入」，运行时与权限管「执行边界」，验证流水线管「输出可信度」，溯源与度量管「可追责与可改进」，成本与模型治理管「资源」，知识沉淀让整个体系越用越好。
