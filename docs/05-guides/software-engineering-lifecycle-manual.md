## 第1章 概述

### 1.1 项目背景

软件工程全生命周期管理平台（Software Engineering Management System, SEMS）旨在为软件项目提供从需求分析到运维支持的全流程管理能力，覆盖需求工程、架构设计、编码实现、测试验证、配置管理、质量保证、项目管理、部署运维等核心领域。

### 1.2 设计目标

| 目标 | 描述 |
|------|------|
| 全流程覆盖 | 覆盖软件生命周期所有阶段 |
| 标准合规 | 符合国标/行标/国际标准 |
| 可追溯 | 需求→设计→代码→测试全链路追踪 |
| 可度量 | 关键指标可量化、可对比 |
| 可改进 | 基于数据驱动的持续改进 |
| AI赋能 | 支持AI Agent辅助全流程 |

### 1.3 适用范围

- 中小型软件项目（5-50人团队）
- 敏捷/混合开发模式
- 支持Web/移动/嵌入式/桌面应用

#### 2.3.2 需求质量准则（INVEST）

| 原则 | 英文 | 含义 |
|------|------|------|
| I | Independent | 独立的，尽量减少依赖 |
| N | Negotiable | 可协商的，非合同条款 |
| V | Valuable | 有价值的，对用户/业务有价值 |
| E | Estimable | 可估算的，可评估工作量 |
| S | Small | 小的，可在一个迭代内完成 |
| T | Testable | 可测试的，有明确的验收标准 |

#### 2.3.3 验收标准格式（Given-When-Then）

```gherkin
Feature: 用户登录
  Scenario: 正常登录
    Given 用户已注册且账号状态正常
    When 用户输入正确的用户名和密码
    Then 系统返回登录成功并跳转到首页
    
  Scenario: 密码错误
    Given 用户已注册且账号状态正常
    When 用户输入错误的密码
    Then 系统提示"用户名或密码错误"
    And 登录失败次数+1
    
  Scenario: 账号锁定
    Given 用户连续5次输入错误密码
    When 用户再次尝试登录
    Then 系统提示"账号已锁定，请30分钟后重试"
```

### 3.3 架构决策记录（ADR）

```markdown
# ADR-001: 选择微服务架构

## 状态：已接受

## 背景
系统需要支持独立部署、独立扩展，团队规模超过20人。

## 决策
采用微服务架构，使用Spring Cloud作为基础框架。

## 理由
- 独立部署降低发布风险
- 独立扩展应对流量高峰
- 团队可独立开发各自服务

## 后果
- 正面：灵活性高、可扩展
- 负面：运维复杂度增加、分布式事务处理
- 风险：服务间通信延迟
```

## 第4章 详细设计

### 4.1 模块设计

#### 4.1.1 模块划分原则

| 原则 | 说明 |
|------|------|
| 高内聚 | 模块内部功能紧密相关 |
| 低耦合 | 模块间依赖最小化 |
| 单一职责 | 一个模块只做一件事 |
| 信息隐藏 | 隐藏内部实现细节 |
| 接口隔离 | 不依赖不需要的接口 |

#### 4.1.2 耦合度度量

| 度量 | 公式 | 含义 |
|------|------|------|
| CBO | Coupling Between Objects | 类间耦合数 |
| Ca | Afferent Coupling | 传入耦合（被依赖数） |
| Ce | Efferent Coupling | 传出耦合（依赖他人数） |
| I | Ce/(Ca+Ce) | 不稳定性指标 |

### 4.2 接口设计

#### 4.2.1 RESTful API设计规范

| 规范项 | 要求 | 示例 |
|--------|------|------|
| 资源命名 | 名词复数 | /api/v1/users |
| HTTP方法 | 语义化 | GET查/POST增/PUT改/DELETE删 |
| 状态码 | 标准化 | 200/201/400/401/404/500 |
| 版本管理 | URL中包含版本 | /api/v1/ |
| 分页 | 标准参数 | ?page=1&size=20 |
| 错误响应 | 统一结构 | {code, message, data} |
| 幂等性 | 写操作幂等 | PUT/DELETE |

#### 4.2.2 接口文档（OpenAPI 3.0）

```yaml

info:
  title: SEMS API
  version: 1.0.0
paths:
  /api/v1/users/{id}:
    get:

        - name: id
          in: path
          required: true

            type: integer
      responses:
        '200':
          description: 成功

            application/json:

### 8.3 质量门禁验证手段详解

每道门禁必须回答三个问题：**谁来证明？用什么数据？存在哪里？**

#### Gate1：需求→设计

| 通过条件 | 验证手段 | 数据来源 | 证据存储 | 执行人 |
|---------|---------|---------|---------|--------|
| 需求评审通过 | 评审会议+签字 | 评审记录TPL-RVW | Git/docs/reviews/RVW-REQ-XXX.md | PM主持，全员签字 |
| 干系人签字 | 电子/纸质签字 | 审批流/OA系统 | OA审批单号或Git签名commit | PM收集 |
| 无歧义/遗漏 | 检查清单逐项确认 | SRS完整性检查表 | 检查表附在评审记录中 | QA |
| RTM已建立 | RTM双向查询 | RTM工具/Excel | RTM文件versioned in Git | BA/PM |

**自我判定方法：** 打开 `docs/reviews/` 目录，找到本次需求的评审记录，确认：①签字齐全 ②问题清单全部"已关闭" ③RTM文件存在且版本号匹配。三项缺一不可。

#### Gate2：设计→编码

| 通过条件 | 验证手段 | 数据来源 | 证据存储 | 执行人 |
|---------|---------|---------|---------|--------|
| 设计评审通过 | 评审会议+签字 | TPL-RVW | Git/docs/reviews/RVW-DES-XXX.md | Arch主持 |
| 接口契约确认 | 消费方书面确认 | 邮件/IM/PR评论 | 确认记录截图存入docs/api-confirmations/ | API Owner |
| DB脚本评审 | DBA评审签字 | DBA评审记录 | Git/db/migrations/REVIEWS.md | DBA |
| 非功能需求有设计策略 | 设计文档检查 | HLD §非功能章节 | HLD文档 | Arch |

**自我判定方法：** 检查设计评审记录签字 + 接口确认记录 + DBA评审记录。若涉及接口变更，必须有至少一个消费方的书面确认。

#### Gate3：编码→测试

| 通过条件 | 验证手段 | 数据来源 | 证据存储 | 执行人 |
|---------|---------|---------|---------|--------|

| 静态分析0 Blocker | SonarQube Quality Gate | SonarQube Dashboard | SQ Project URL | CI自动 |
| 变更未越界 | `git diff --name-only` vs 变更范围清单 | Git + TPL-CS | Diff输出附在PR描述中 | Reviewer |

**自我判定方法：** 打开PR页面，确认：①≥1个Approve ②CI状态绿色 ③SonarQube Quality Gate Passed ④覆盖率数字≥80% ⑤diff文件列表⊆变更范围清单。任一不满足则Gate3未过。

## 第16章 反向传播分析（影响分析）

### 16.1 定义

从变更点出发，沿**被调用方向（逆向）**遍历，找出所有**依赖本次变更**的下游接口与功能。

### 16.2 关键区别

| 分析方向 | 问题 | 术语 |
|---------|------|------|
| 正向 | 我改了谁？我调用了谁？ | 涉及分析 |
| 逆向 | 谁依赖我？谁会被我影响？ | 影响分析 |

### 16.3 影响面评估矩阵

| 受影响接口 | 耦合类型 | 影响程度 | 风险等级 | 需要验证？ |
|-----------|---------|---------|---------|----------|
| POST /auth/login | 直接耦合 | 高 | 🔴 | ✅ 必须 |
| POST /auth/mfa/verify | 新增 | 高 | 🔴 | ✅ 必须 |
| GET /user/profile | 数据耦合 | 中 | 🟡 | ✅ 必须 |
| AdminController | 直接耦合 | 中 | 🟡 | ✅ 必须 |
| 第三方SSO | 接口耦合 | 高 | 🔴 | ✅ 必须 |
| 登录报表 | 数据耦合 | 低 | 🟢 | ⚠️ 抽检 |
| 用户注册 | 无耦合 | 无 | 🟢 | ❌ 不需要 |

### 16.4 耦合度量化指标

| 指标 | 全称 | 含义 | 阈值 |
|------|------|------|------|
| CBO | Coupling Between Objects | 类间耦合数 | >10需警惕 |
| Ca | Afferent Coupling | 被依赖数 | 越高影响面越大 |
| Ce | Efferent Coupling | 依赖他人数 | 越高越脆弱 |
| I | Instability | Ce/(Ca+Ce) | →1表示不稳定 |

**决策依据：** 当变更点的Ca值高时，意味着有大量下游依赖者，必须扩大回归范围。

## 第17章 回归测试决策

### 17.1 理论依据

**Rothermel-Harrold算法（1996）：**

> 给定原始程序P、修改后程序P'、以及原始测试套件T，选择一个子集T' ⊆ T，使得T'能覆盖P与P'之间所有行为差异。

**核心公式：**

```
回归测试集 = 直接受影响用例 ∪ 间接受影响用例 ∪ 风险驱动补充用例
```

### 17.2 回归决策矩阵

| 变更类型 | 回归决策 | 回归范围 | 回归深度 |
|---------|---------|---------|---------|
| 新增功能（不修改已有代码） | 需要 | 新功能+冒烟 | 浅 |
| 修改已有功能逻辑 | 必须 | 受影响+直接依赖 | 中 |
| 修改接口签名 | 必须 | 所有消费方+集成 | 深 |
| 修改数据库表结构 | 必须 | 所有读写该表的模块 | 深 |
| 修改公共组件 | 必须 | 所有使用该组件的模块 | 深 |
| 修改配置项 | 需要 | 读取该配置的模块 | 中 |
| 修改第三方依赖版本 | 必须 | 所有使用该依赖的功能 | 深 |
| 纯文案/样式 | 抽检 | 仅修改页面 | 浅 |

### 17.3 回归分层策略

| 层级 | 用例类型 | 选择策略 | 执行方式 |
|------|---------|---------|---------|
| L0 冒烟 | 核心业务流程 | 每次必选 | 100%自动化 |
| L1 精准 | 与变更代码有映射的用例 | 调用链分析 | 自动化为主 |
| L2 影响面 | 受影响接口的集成测试 | 影响矩阵 | 自动化+手工 |
| L3 全量 | 所有用例 | 仅重大版本 | 自动化+手工 |

### 17.4 决策规则

```
IF 变更类型 == "修改接口签名" OR "修改公共组件" OR "修改数据库结构":
    回归级别 = L2
    IF 影响面覆盖核心业务:
        回归级别 = L3

ELIF 变更类型 == "修改已有功能逻辑":
    回归级别 = L1 + L0

ELIF 变更类型 == "新增功能":
    回归级别 = L0 + 新功能验证

ELIF 变更类型 == "纯文案/样式":
    回归级别 = 抽检
```

@mcp.tool()
def analyze_change_scope(
    change_description: str,
    change_type: str,
    project_root: str,
    related_requirements: Optional[List[str]] = None
) -> dict:
    """分析变更范围（三层影响分析）"""
    affected_requirements = _trace_requirements(change_description, related_requirements)
    affected_modules, affected_interfaces = _analyze_design_impact(affected_requirements, project_root)
    affected_files = _analyze_code_impact(affected_modules, project_root)
    affected_db = _analyze_db_impact(affected_files, project_root)
    affected_config = _analyze_config_impact(affected_files, project_root)
    
    return {
        "affected_requirements": affected_requirements,
        "affected_modules": affected_modules,
        "affected_files": affected_files,
        "affected_interfaces": affected_interfaces,
        "affected_database": affected_db,
        "affected_config": affected_config,
        "confidence_score": _calculate_confidence(affected_files),
        "analysis_method": "rtm_trace + call_graph + static_analysis"
    }

@mcp.tool()
def get_dependency_graph(
    target: str,
    direction: str,
    depth: int = 3,
    include_cross_module: bool = True
) -> dict:
    """获取依赖图"""
    graph = _build_call_graph(target, direction, depth, include_cross_module)
    return {
        "target": target,
        "direction": direction,
        "nodes": graph["nodes"],
        "edges": graph["edges"],
        "coupling_metrics": _calculate_coupling(graph)
    }

@mcp.tool()
def assess_impact(change_scope: dict, risk_threshold: str = "medium") -> dict:
    """影响面风险评估"""
    matrix = []
    for interface in change_scope.get("affected_interfaces", []):
        coupling_type = _determine_coupling_type(interface)
        impact_level = _assess_impact_level(interface, coupling_type)
        risk_level = _calculate_risk(impact_level, coupling_type)
        matrix.append({
            "target": interface,
            "coupling_type": coupling_type,
            "impact_level": impact_level,
            "risk_level": risk_level,
            "needs_verification": risk_level in ["high", "medium"]
        })
    return {"impact_matrix": matrix, "overall_risk": _calculate_overall_risk(matrix)}

@mcp.tool()
def select_regression_tests(
    change_scope: dict,
    impact_assessment: Optional[dict] = None,
    regression_level: str = "auto"
) -> dict:
    """回归测试选择"""
    if regression_level == "auto":
        regression_level = _auto_decide_level(change_scope, impact_assessment)
    
    smoke_tests = _get_smoke_tests()
    selected = smoke_tests
    
    if regression_level in ["L1_precision", "L2_impact", "L3_full"]:
        selected += _select_by_call_graph(change_scope)
    if regression_level in ["L2_impact", "L3_full"]:
        selected += _select_by_impact_matrix(impact_assessment)
    if regression_level == "L3_full":
        selected = _get_all_tests()
    
    return {
        "regression_level": regression_level,
        "selected_tests": selected,
        "estimated_duration": _estimate_duration(selected),
        "coverage_of_change": _calculate_coverage(selected, change_scope)
    }

def generate_spec(

        "constraints": _extract_constraints(requirement),
        "edge_cases": _identify_edge_cases(requirement),
        "out_of_scope": _define_boundaries(requirement),
        "test_specification": _generate_test_spec(requirement) if include_test_spec else None
    }

| 范围约束 | 只能修改变更范围内的文件 | 自动阻断 |
| 规范约束 | 遵循项目编码规范 | 静态分析不通过 |
| 测试约束 | 每个公开方法必须有测试 | 覆盖率不达标 |
| 复杂度约束 | 圈复杂度 ≤ 10 | 静态分析告警 |
| 安全约束 | 无SQL注入/XSS等漏洞 | 安全扫描不通过 |
| 依赖约束 | 不引入未批准的第三方库 | 依赖审查不通过 |

#### AI辅助（MCP工具调用）

```
1. 调用 T14 get_architecture_context(aspect="coding_standards")

   → 搜索现有实现

3. 使用 Prompt: code_implementation
   → 注入Spec+规范+文件范围，AI生成代码

| 阶段 | 检查项数 | 核心内容 |

## 第34章 反模式与常见失败清单

> 本章列出实践中最常见的失败模式。团队应定期对照自查，避免踩坑。

### 34.1 需求阶段反模式

| # | 反模式 | 症状 | 后果 | 正确做法 |
|---|--------|------|------|---------|
| R01 | 需求不评审就开发 | "大家都懂了"跳过评审 | 理解不一致，返工率>30% | 必须走Gate1，哪怕简化为30分钟走查 |
| R02 | 验收标准缺失 | 只有功能描述没有AC | 测试无法验证，上线后扯皮 | 每条需求必须有Given-When-Then |
| R03 | 需求追踪断裂 | RTM只在立项时建，后续不维护 | 变更时无法追溯影响 | 每次变更同步更新RTM |
| R04 | 黄金需求 | 一条需求包含5+个功能点 | 无法估算、无法测试、无法拆分 | 按INVEST拆分，每条≤1个迭代 |
| R05 | 口头需求 | "上次说的那个" | 无据可查，责任不清 | 所有需求必须文字化并入库 |

### 34.2 编码阶段反模式

| # | 反模式 | 症状 | 后果 | 正确做法 |
|---|--------|------|------|---------|
| R06 | 覆盖率虚高 | 覆盖率90%但断言为空/弱 | 测试无效，缺陷逃逸 | 审查断言质量，不仅看数字 |
| R07 | AI无约束编码 | AI自由发挥超出Spec范围 | 引入未设计的功能/副作用 | 严格限定变更范围+Spec约束 |
| R08 | 跳过自审 | 写完直接提PR | Reviewer发现大量低级问题 | TDD+Reflection后再提PR |
| R09 | 魔法值硬编码 | `if (status == 3)` | 可读性差，修改易出错 | 枚举/常量+注释 |
| R10 | 异常吞没 | `catch(Exception e) {}` | 问题被隐藏，排查困难 | 至少记录日志，优先处理 |

### 34.3 测试阶段反模式

| # | 反模式 | 症状 | 后果 | 正确做法 |
|---|--------|------|------|---------|
| R11 | 回归只跑冒烟 | "时间不够只跑L0" | 影响面缺陷逃逸 | 至少L0+L1，用T04自动选择 |
| R12 | 测试环境与生产差异大 | "测试环境好好的" | 上线即故障 | 预发布环境必须与生产一致 |
| R13 | 缺陷不复现就关闭 | "我这边没问题" | 间歇性缺陷累积 | 必须复现或有日志证据才能关闭 |
| R14 | 测试数据污染 | 测试用例互相干扰 | 结果不可靠 | 每个用例独立数据，用完清理 |
| R15 | 只测Happy Path | 只测正常流程 | 边界/异常缺陷多 | 等价类+边界值+错误猜测 |

### 34.4 变更与发布反模式

| # | 反模式 | 症状 | 后果 | 正确做法 |
|---|--------|------|------|---------|
| R16 | CIA走过场 | "改了一行代码不用分析" | 小改动引发大故障 | 任何变更都走CIA，哪怕5分钟快速版 |
| R17 | 无回滚方案就发布 | "应该没问题" | 故障时手忙脚乱 | 回滚方案是发布准入条件 |
| R18 | 周五下午发布 | "赶在周末前上" | 周末无人值守，故障扩大 | 发布窗口避开节假日/周末 |
| R19 | 变更不记录 | 直接改配置/数据库 | 无法追溯，审计失败 | 所有变更走CR流程 |
| R20 | 门禁豁免常态化 | 每次都"紧急放行" | 门禁形同虚设 | 豁免率>10%需复盘流程 |

### D.1 SRS片段填写示例（FR-001 用户登录）

```markdown
#### FR-001: 用户登录

- **描述：** 已注册用户通过用户名和密码登录系统，支持记住登录状态
- **输入：** username(string, 必填), password(string, 必填), remember_me(boolean, 可选)
- **处理逻辑：**
  1. 校验用户名密码
  2. 检查账号状态（正常/锁定/禁用）
  3. 生成JWT Token
  4. 记录登录审计日志
  5. 若remember_me=true，设置长期Token
- **输出：** {token, expires_at, user_profile}
- **验收标准：**
  - Given 用户已注册且状态正常 When 输入正确凭证 Then 返回token且跳转首页
  - Given 用户已注册 When 输入错误密码 Then 提示"用户名或密码错误"且失败计数+1
  - Given 连续5次错误 When 再次尝试 Then 提示"账号已锁定30分钟"
  - Given remember_me=true When 登录成功 Then Token有效期30天
- **优先级：** Must
- **关联需求ID：** REQ-2026-001
- **非功能约束：** 登录接口P99<300ms，密码传输TLS加密，失败5次锁定
```
