## Problem

版本号现在有两套并行、互不一致的表示：

1. **文件版本**（exe 属性、设置页显示、更新判定用的"当前版本"）= `2.2.<yyyy>.<MMdd>`（构建日期自动生成，如 `2.2.2026.1002`）；
2. **发行号**（git tag / `versions/<ver>/` 目录名 / zip 名 / 更新语义）= 人工指定（如 `v2.2.12`、`v2.2.2026.0930`）。

两者"各司其职"（真源 §1.1 原文），导致同一个发布在三处显示三个不同的串：exe 属性 `2.2.2026.1002`、目录名 `2.2.12`、tag `v2.2.2026.0930`。用户要求统一为图片所示形态：**三段版本号 + 第 4 段时间编码**。

## Why

- **一眼可读**：`2.3.0.2609161125` 同时表达"哪个版本线（2.3.0）"与"什么时候出的（2026-09-16 11:25）"，排查/回溯不必再做脑内映射。
- **单一真源**：tag、目录名、zip 名、两个 exe 的文件版本、设置页"当前版本"是同一个串，消除"哪个才是真版本"的歧义，回滚时也不会拿错目录。
- **与既有链路同构**：`versions/<ver>/` 与 `versions/current` 天然按目录名寻址（`update-agent.ps1` 只认字符串），统一后更新链无需额外映射表。

## Expected Outcome

用户拿到一份"版本号唯一"的发布：

- 发行号（tag）＝ 版本目录名 ＝ zip 名中的版本 ＝ 两个 exe 的 `FileVersion`/`ProductVersion` ＝ 设置页「当前版本」＝ **`<三段版本号>.<yyMMddHHmm>`**（示例 `2.3.0.2609161125`）；
- 已安装的旧规则实例（`2.2.2026.x`）升级后仍能从新规则版本**收到更新**（不因规则换代而静默断链）；
- 真源文档与 `AGENTS.md` 描述与新规则一致，仓库内无残留旧规则描述。

## Constraints

- 不改数据库结构、鉴权/权限/支付/安全核心逻辑，不新增第三方依赖，不做无关重构。
- 遵守 Windows PE 文件版本的既有事实：每段 16 位（>65535 触发 CS7035 且数值字段被截断）——实测见 `00-repository-understanding.md` 探针节。
- 保持"本地与 CI 同一命令"契约（`release-local.ps1`），CI 仍由 tag 触发，`-Version` 语义不变。
- 严禁 agent 停/启/杀用户运行中的宿主进程（本次只做只读核对与本地构建验证）。
- 不破坏既有 e2e 断言（`e2e/update-live-apply.spec.ts:91`：更新后 `currentVersion` 以目标 tag（去 v）开头）。

## Success Criteria

- [ ] 三段 + 时间编码：发行串形态为 `<major>.<minor>.<patch>.<yyMMddHHmm>`（10 位时间编码），一处生成、全程复用。
- [ ] 一致性：同一发布的 tag / `versions/<ver>/` / zip 名 / 两个 exe 的 `FileVersion` / 设置页显示串完全相同（可被脚本断言）。
- [ ] 解析健壮：10 位时间编码不再因 `int` 溢出被丢弃；`2.3.0.2609161125` 能被正确解析与比较。
- [ ] 升级不断链：`2.2.2026.1002`（旧规则）→ 新规则版本能被判定为"有更新"（单测覆盖）。
- [ ] 文档同步：真源 `packaging-upgrade-backup.md` §1.1 与变更记录、`AGENTS.md` §2.3 与本规则一致。
- [ ] 验证可见：`dotnet build` 与相关 `dotnet test` 通过，且发布脚本干跑产物名/目录名/两 exe 版本号可核。
