# Intent

## 为什么（用户原话，逐字）

- 输入21（2026-10-04 23:4x）：「另一个会话已经提交 docs/ai/pilot/2026-10-04-host-install-root-single-source 设计系统的也发布最新，**你截图展厅看看，展厅预览区太小，看不全**」
- 输入22（2026-10-04 23:5x，即本任务闸门1 拍板）：「**展厅展示，应该缩放，或者可以最大化，或者可以自由调尺寸，并且有滚动条，不能只看到部分**」

展厅是设计系统插件的主出口（挑预设 → 看效果 → 微调 → 存为新设计）。预览区"只看到一部分"等于这个插件最有说服力的那一步没有证据可看。

## 做什么（需求拆解为可验证项）

| # | 需求（用户话） | 落成的行为 | 成功判据（数字/命令输出） |
|---|---|---|---|
| R1 | 应该缩放 | 「适应」档：整页按可用宽等比缩放，`k = min(1, 可用宽/稿宽)`，默认档 | 1372x768 下读数 < 100% 且横向溢出 ≤ 2px；框右缘不越过容器内容右缘 |
| R2 | 不能只看到部分 | 任何档位的每一像素都**可达**：1:1 / 最大化档下滚到末端后稿的右边缘进入可见区 | `scrollLeft` 可达 `scrollWidth-clientWidth`；末端时框右缘 ≤ 容器左缘 + 可用宽 |
| R3 | 可以最大化 | 「最大化」档让开两侧栏（网格塌单列、舞台排到最前） | `grid-template-columns` 计算值只剩一条轨道；画布可用宽 ≥ 三列时的 1.5× |
| R4 | 可以自由调尺寸 | 画布盒原生 `resize`（fit 拖宽、actual/max 拖宽拖高），拖完缩放比**重算** | 真鼠标拖右下角：盒宽至少缩 40px，且读数跟着下降（数值不写死，避免随栏宽策略变动而失真） |
| R5 | 并且有滚动条 | 溢出即由滚动条/滚轮承接 + 非适应档给出提示行说明"画布外还有东西、怎么到达" | `[data-stage-hint]` 在 1:1/最大化在场、在适应档不在 |
| R6 | （隐含）别每次重新点 | 档位记忆到 localStorage，刷新不丢；脏值回落默认档 | 切 1:1 → 刷新仍 1:1；存储写 `maximise` → 刷新回落「适应」且舞台在 |

## 到什么程度（边界）

- 只改插件前端 + 插件层 e2e + 插件 README/文档；**不动**后端、导出/投影文本、宿主源码、宿主前端。
- 不放大：`k` 上限恒为 1。1280 的稿在 1920 窗口下按 1:1 显示，富余的宽度留给"最大化"，不做超出真实设计尺寸的放大（放大会让字距与留白失真）。
- 不承诺"滚动条常驻可见"：本机 Chrome 的滚动条是浮层式（实测自定义 `::-webkit-scrollbar` 一个像素都不画，见 05-evidence 的探针记录）⇒ 这条属于浏览器策略，本插件只兑现"可达 + 说明"。
- 不新造拖拽数学（不自研 mousedown/mousemove），用原生 `resize` + `overflow:auto`。

## 不做什么（NOT-to-do）

- 不做"折叠成 48px 图标条"的侧栏（输入21 方案里的 S3）——输入22 的"可以最大化"覆盖了同一诉求，且整列让位比每栏一个折叠开关更少状态、更少判据。
- 不改 M2 已交付的取数/换装窗口逻辑（G17）、微调不落库口径、对比区作用域隔离。
- 不引入新依赖（不加 `@vueuse/core` 之类拿 `useResizeObserver`）。
