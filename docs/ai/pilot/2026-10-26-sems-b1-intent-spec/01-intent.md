# Intent

> 阶段：Stage 1｜只回答为什么做、做什么、做到什么程度，不提前锁定代码实现。
> Task ID：2026-10-26-sems-b1-intent-spec

## Problem

Coding Agent 成为主要代码生产者后，瓶颈在于说清意图。Sems 目前管理的是项目档案与进程，没有记录「要做什么、做到什么算完成」的结构化位置。Agent 和评审者缺少客观依据，需求也没有与代码变更关联。

## Why

- 来源：Plugins/Sems/docs/requirements.md 4.5 的 B1（意图与规格层），用户 2026-10-26 要求开始做 B1。
- B1 是方案 B 中承接「规格」的要素；B6 验证流水线要把验收标准转成可执行检查，需要规格作为输入。
- 规格是「源代码的源代码」，不版本化则无法追溯某次变更当时依据的是什么。

## Expected Outcome

在 Sems 中能够：

- 结构化地记录需求、验收标准、约束与任务拆解（B1-FR1）。
- 在规格与代码变更之间双向查询（B1-FR2）。
- 标记每条验收标准是否已有对应测试或评测用例（B1-FR3）。
- 规格修改留痕，旧版本可查，已有关联指向生成时的版本（B1-FR4）。

## Constraints（逐条对照规范 §1）

- 不修改生产环境：满足。
- 不改数据库结构：存在冲突风险。若选插件自有实体库即新增库表，须闸门 1 明文授权；选「落文件」或「只读索引」则不触发。
- 不改鉴权、权限、支付、安全核心逻辑：满足；新增管理端点沿用类级 [Authorize("ApiKeyPolicy")]，不改既有鉴权。
- 不新增大规模依赖：满足；仅用 NewLife.Core 等现有依赖（若选实体库，需确认 XCode 引用方式，属现有体系）。
- 不做无关重构：满足。
- 不改与本任务无关文件：满足；既有 13 个 sems_* 工具的行为不变。
- 必须能运行实际测试或构建验证：满足，见 03。
- 结论基于真实仓库内容：Controllers/ 与 web/ 未读的部分标 Unknown。

## Success Criteria

以下标准均须能被实际验证判定：

- B1-AC1：给定一条规格，能列出全部关联变更；给定一个变更，能显示所依据的规格及版本。
- B1-AC2：给定含 N 条验收标准的规格，能显示每条标准是否已关联用例。
- B1-AC3：修改规格后旧版本仍可查看，已有关联变更仍指向其生成时的规格版本。
- 构建与相关测试通过，且判据看日志正文，不拿 exit code 当证据。
- 既有 13 个 sems_* 工具的回归测试保持通过。
