| 层 | 定义 | 现有实例 | 允许 | 禁止 |

| T1 平台公共插件 | 被多个无依赖插件需要的公共能力唯一宿主 | mcp-center（MCP 网关 + 公共工具宿主，双职责） | 公共工具、协议网关、工具发现 | 吞并某个领域插件的完整域 |

## FR-2 域判定三问（「不多不少」的操作化）

1. **越界问（不多）**：删掉这个功能，插件的核心使命是否依旧完整？——是 → 功能越界，应迁出。
2. **缺位问（不少）**：插件域内的自然需求，是否必须跨插件拼凑才能完成？——是 → 评估补齐或显式声明消费关系。
3. **归属问（唯一）**：这个功能换个插件是否同样放得下？——是 → 按两条定唯一归属：**实体归属**（功能的实体/数据/表在哪边）优先于**消费便利**（谁先用谁实现）。

## FR-3 六条可执行条款

1. **一插件一域**：plugin.json `Description` 首句即域声明；全部工具/服务/持久化实体必须能归入域声明，否则越界。
2. **消费≠实现（T3 铁律）**：T3 需要领域能力 → 经注册表/`ctx.Get<T>()` 消费；能力不存在 → 给属主提需求或立新插件；禁止「因为我要用所以我自己实现」（AIAgent 文件三件套反例）。
3. **公共能力唯一归属**：被 ≥2 个互不依赖的插件需要的能力，唯一归属 T1 或宿主；**T2 之间禁止同功能双实现**（text/dev 三对重复反例）。
4. **依赖方向**：T3→T2/T1 单向消费；T2↔T2 只经 Abstractions 契约（L1 默认，事件 L2 需确认偏差#5 已修）；禁止 T2→T3、禁止循环依赖。
5. **名字稳定与归属解耦**：工具实现可迁属主插件，平台保留名/公共名不因迁移改名（运行时协议稳定性优先）。
6. **准入流程**：新功能先查归属（现有插件域内？）→ 无属主 → `plugin-feasibility-study` 评估立新插件 → 公共能力归 T1 → 都不是 = 宿主内核候选（须 ADR）。

## FR-4 审计输出格式

逐插件一行：`插件 | 层 | 判定(✅/⚠️/❌) | 依据条款 | 发现与建议`。违规项必须含：归属建议 + 搬迁代价 + 触发条件（拍板后另开任务实施，本批不动代码）。

## FR-5 Interaction Design

不涉及用户可见 UI（标准文档 + 审计报告），无交互设计节。
