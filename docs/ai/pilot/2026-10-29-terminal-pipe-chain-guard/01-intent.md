# Intent

> 阶段：Stage 1｜Task ID：PILOT-075｜日期：2026-10-29
> 来源：用户输入5（2026-10-29 15:31）：「关于执行命令工具，关于命令的拦截，禁止管道和链式不合理，放开支持，每一个管道或者链式，应都走同样的拦截校验」

## Problem

命令执行安全门的第 2 道门是**整串字符级拒绝**：命令里出现 `|` `;` `&` `<` `>` 反引号或换行任一字符即拒
（`TerminalCommandGuard.cs:106-119`、`CommandGuard.cs:97-111`）。后果：

1. `git status && git diff`、`dotnet build; dotnet test`、`git log | node count.js` 这类日常组合全被拒，
   模型只能拆成多次工具调用（每多一次调用 = 多一次往返与出错面）；
2. **引号内的分隔符也被误杀**：`pwsh -NoProfile -Command "Get-Process | Select-Object -First 3"` 因字符串里有 `|` 被拒，
   与 shell 语义相悖；
3. 用户裁定：禁止管道和链式不合理，应放开；放开的正确姿势是**每一个管道/链式段落都走同样的拦截校验**
   （而不是把分隔符放进来不管）。

## Why

要防的安全风险是「借管道/链式夹带破坏性命令」（如 `git status && rm -rf x`），而不是分隔符本身。
把校验模型从「整串字符黑名单」升级为「引号感知分段 + 逐段过同一套白名单/破坏性红线」，安全性不降级
（破坏段仍被拦，且拒绝原因能指出是第几段），同时恢复管道/链式表达力——这正是用户指出的方向。

## Expected Outcome

- `|`、`&&`、`||`、`;`、换行分隔的多段命令可执行；每段独立通过与单命令**完全相同**的三道门校验
  （可执行名裸名 → 白名单 → 破坏性红线：位置参数/内联代码/EncodedCommand）；
- 引号内的 `|` `;` `&&` 不再被当作分隔符（与 pwsh 语义一致）；
- 重定向（`<` `>`）、反引号、后台单 `&`、空段、引号不配对**仍整串拒绝**；
- 两份守卫实现（mcp-center / tool-bridge）逐条同判同因（对账金样表扩展）；
- 模型可见文案（工具 Description / JSON Schema / tool-bridge 提示词）与实现同步。
