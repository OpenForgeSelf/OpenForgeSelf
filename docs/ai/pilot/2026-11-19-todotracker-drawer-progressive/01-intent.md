# Intent

> Task ID：`2026-11-19-todotracker-drawer-progressive`｜日期：2026-11-19

## Problem

1. **创建心智负担**：用户只想「先记一笔」，但界面立刻用「还缺」红字与整页工作单元表单施压，仿佛创建时就要填齐下发字段。  
2. **编辑挤压**：选中任务后右侧分栏吃掉主区宽度，列表/看板被挤窄，浏览与编辑互相抢空间。  
3. **一次信息过载**：详情/编辑共用面板却一次铺开过多字段；分类不够清晰，首屏看不到「现在该做什么」。

## Why

待办的主路径是「快速捕获 → 择机补齐 → 关键节点（下发前）硬校验」。当前壳层把「补齐」与「浏览」绑在同一分栏里，既打断捕获，也破坏浏览。侧边抽屉 + 渐进披露能让列表保持全宽，把深度编辑移到叠层，并把必填校验留在真正不得不填的步骤。

## Expected Outcome

- 新建：标题即可落库；列表不因缺四栏显示错误态文案（可软提示「下发前待补齐」）。  
- 点开任务：右侧抽屉打开，列表/看板宽度不变。  
- 详情与编辑同一抽屉壳；首屏只见摘要与分类入口，按门类展开后再编辑。  
- 下发/委派前硬校验四栏；缺项时点名反馈，不静默失败。  
- 先交付可审原型截图；闸门1 批准后再改插件代码。

## Constraints

- 不改数据库结构、不改 Create/Dispatch API 契约形状。  
- 创建仍仅强制 `title`；下发必填仍走 `DispatchPayloadBuilder.Missing`。  
- 抽屉须避免宿主裁切（参考 PC-012：弹层挂 body）。  
- 不引入新 UI 框架依赖；优先 Element Plus `el-drawer` 或现有 token 自绘。  
- 闸门1 未批前不改业务实现代码（本回合只整理需求 + 原型截图）。

## Success Criteria

1. 六段方案与 Spec（含 Interaction Design）落盘且用户能指出路径审阅。  
2. 原型至少覆盖：全宽列表、抽屉打开、渐进分类、下发前缺项反馈；截图可在 artifacts 打开。  
3. 闸门1 批准后的实现：插件 build + 相关单测 + 1 条冒烟 e2e + 设计门禁按 §5.6 快档绿。
