## 审查八问

**1. 实现是否真正满足 Intent？**
满足。Intent 是"从前端玩具变成有完整设计功能的插件"，判据不是功能数量而是**每条能力背后有没有真东西**。本轮由验证揪出并修掉的四个"看起来有、其实是假的"：
① `tokens/effective` 的 `colorHex/contrastRatio` 是占位假字段；② 导出 CSS 里复合令牌是空声明（`--ds-shadow-elevation-1: ;`）；③ 项目"令牌数"读的是没人维护的缓存列（显示 0）；④ 密度主题只换名字不换尺度（`space.4` 两主题同为 8px）。
这四条现在都有测试或 e2e 断言钉住。

**2. 实现是否符合 Spec？**
符合，含两处**已记录的口径修订**（`02-spec.md` 末节）：AC17（微调=参数重生成，不做前端草稿态）、AC20（取消 TS 侧色彩数学镜像）。其余 AC1–AC16、AC18–AC21 有 Verified 证据；AC22/AC25 以最后一跑为准；AC23（本地 zip 发布）按用户指令执行中；AC24 文档已回写。

**3. 是否超出了 Scope？**
没有加新业务面，但有**两类额外动作**需要承认：
- 为让"内置零许可证图标"这条用户拍板落地，新增了 `BuiltinIcons`（40 枚自绘）——属原 AC 范围内（FR/图标库），但工作量超出"改改前端"的直观预期；
- 前端下线了 v1 的生成/导出/样张页与未使用组件件（移入 `.trash/`，可恢复）。删除面较大，若评审认为应保留演示页，可回滚该批文件。

**4. 是否修改了不应该修改的文件？**
宿主侧只改了 `ForgeSelf.Api/Data/XCodeConfig.cs`（插件库路径映射的唯一真源）与 `ForgeSelf.Api.Tests.csproj`（引用插件项目）；另按 §2.4 规则登记新技能到 `AGENTS.md`、按 §7 把可复用规律写进 `docs/04-standards/agent-workflow.md`。未动 `.env`/`appsettings.Production.json`，未动用户运行中的宿主，未打 tag。

**5. 测试是否覆盖 Acceptance Criteria？**
后端 163 项（9 个测试文件）+ 前端 vitest 20 项 + 插件层 e2e 一条全链路（17 段断言）。缺口：
- **AC22 的审计→发布负向路径**（critical 拦发布）只在 xUnit 覆盖，e2e 只跑正向；
- **导出体积（U1/T302）无测试**；
- ThemeLab 的"新主题要有内容"只测了后端能力，界面路径未 e2e 化。

**6. 是否存在明显回归风险？**
- `TokenNode` 加了 `Lifecycle/Description` 两个可选位置参数（末位、带默认值）→ 旧构造点不破；`EffectiveToken` 同理，但**新增字段会让"形状敏感"的外部消费方看到多出来的键**（本插件界面已同步）。
- 生成器现在**跳过非色向主题的语义色**并给密度主题铺尺度：已有项目重新生成时，compact 主题会新增尺度行（不是破坏性，但会变数据）。
- `DesignProject.TokenCount/ComponentCount` 不再作为出参来源：如果有别的代码读这两列当真值，需要改（仓内已 grep，只有导出/发布在写它）。
- 全量 `dotnet test` 仍不稳定（测试主机崩溃 + 4 项非本任务失败）→ 不能以"全绿"叙述交付。

**7. 是否存在架构不一致？**
一处刻意不一致需要说明：插件的**预览换肤**用后端 CSS + 前端"变量重键别名表"（`design/skin.ts`），而不是让外壳组件直接读 `--ds-semantic-*`。理由：外壳中性主题与用户系统必须互不污染，且别名表可以按"令牌存在才写"避免悬空引用。它不是第二套设计值实现（只做命名），但确实多了一张需要同步的表 —— 已用单测钉住映射规则（`cssVarName` 与后端 `CssVarName` 同规则）。

**8. Evidence 是否足以证明任务完成？**
`05-evidence.md` 每条标了 Verified/Inferred/Unknown，并保留了失败原文（e2e 五跑的真实失败与修复、宿主 Busy 异常原文）。
最后一步（AC23 本地 zip）的执行结果补在同文件"最终跑"节；**e2e 连跑两跑全绿，未触发本 Decision 的降级条款**。

## Findings

### Critical
- 无（本轮曾有的 5 个"假能力/半玩具"缺陷全部修复并有测试或 e2e 断言：假 effective 字段、空复合导出、
  从不维护的计数列、装饰性密度主题、生成不落组件目录）。

### Major
1. **宿主 SQLite 并发 BUSY 会以 500 冒泡到用户**（实测命中写路径 `AuditRepository.Record`、只读路径
   `DesignProjectService.Find` 与 `tokens/effective`）。本插件侧已做：连接串 `Busy Timeout=5000`、
   只读请求退避重试（写请求不重试）、e2e 客户端同样只重试 Busy。**根因在宿主 DAL，未闭合 → P1 TODO**；
   现在 e2e 绿是"带重试的绿"，不是"零锁冲突的绿"，这条不得被叙述成已修。
2. `catch { return "" }` 类静默失败在投影层出现过（ShadowCss 首版），建议对投影层所有 `catch` 加"返回空即记 warning"的约定。
3. 审计/生成/导出的错误信息目前只到 HTTP body，前端逐条显示，但没有集中"最近 N 条失败"面板（排查依赖打开控制台）。
4. 全量 `dotnet test` 不稳定：不属于本插件，但会让"跑一遍全量"的验收动作失去意义，需要单独治理。

### Minor
1. 项目创建曾出现一次"项目已存在"的重复 POST 日志，UI 未复现失败，原因未定位（记 TODO，不猜）。
2. 组件矩阵厚度受令牌面限制：`card/badge/dialog/tooltip` 这类没有命名空间段的组件只有 `base/default` 一格。
   这是**如实显示**（格子只能由真实令牌反推），不是假数据；要变厚只能继续补真令牌。
3. `capabilities` 里 `audit.read` 与 `audit.run` 未区分只读/写库两条路径，灰化粒度偏粗。
4. ThemeLab 无删除主题入口（后端也没有该端点）——与"实验"心智略有落差，属有意保守（不软删主题数据）。
