# Intent（目录扫描提速 · FileTools 1.1.2）

> 阶段：Stage 1｜本文为 `mini-task.md` §1 的标准模板化拆出件（内容同源，以 mini-task.md 为闸门1 批复原件）。

## Problem

「目录大小排行」的全树扫描过慢：走查实测 `C:\Users\Administrator\.qoder-cn\worktrees`（101,994 文件）耗时 **65,973 ms**（647 µs/文件）。同机 A/B 定位到两个根因：

1. `Walk` 对每个文件做两次独立元数据调用（`File.GetAttributes` + `new FileInfo(e).Length`），而文件系统枚举记录本身就带 size（去掉多余那次 ≈ 1.6×，流式自带 ≈ 8×）；
2. 单线程遍历（并行 DOP=8 叠加流式后 ≈ 10–30×）。

用户原话（输入16，T34）：「当前实现与XCoder码神工具的实现有何差别？为什么码神工具统计文件夹大小这么快，当前实现这么慢？」

## Why

用户在 1.1.1 已可用后明确追问性能差距——性能是「文件夹大小统计」功能可用性的直接部分；且实测证明修复不牺牲正确性就能拿到（1.1.1 的任意时刻分区闭合在提速方案下开销 ≈ 噪声，探针变体 D）。

## Expected Outcome

- 同树扫描耗时降至原来的 **1/8 ~ 1/30**（`Plugins/` 树 22 s → ≤ 3 s；线上锚点树 66 s → ≤ 15 s）。
- 对外契约（端点、字段、鉴权）、交互、中间态自洽性全部不变。
- 以插件 1.1.2 侧载交付，宿主不重启（输入2）。

## Constraints

- 只改 `Plugins/FileTools/` 内 2 个代码文件 + 2 个版本号文件；宿主零改动。
- 不引入任何新依赖；不加缓存、不做懒展开、不做删除（输入12 拍板：归批次D）。
- 保留 1.1.1 全部语义：reparse 跳过、权限/IO 逐条容错、200k 目录 / 5M 文件上限、取消、**任意时刻分区闭合**。
- 并行度默认值、计时阈值策略：闸门1 已拍板 = `min(ProcessorCount, 8)`、绝对阈值（12k 夹具 ≤ 1500 ms）（输入42 T42 默认确认）。

## Success Criteria

1. 同树 `Plugins/`（51,931 文件 / 7,004 目录）扫描 **≤ 3 s**（当前实测 22 s）。
2. 线上锚点树（101,994 文件）**≤ 15 s**（当前 65,973 ms）。
3. `e2e/plugins/file-tools` **6/6 绿**，中间态断言不退化。
4. 取消 → `Cancelled` 且部分结果闭合；上限截断语义不变（均有测试断言）。
