**问题 1：产品前提从未被外部验证**

| 项         | 内容                                                                                                                                                                                                                                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 问题       | Kit 的目标用户是独立开发者和小团队，但全部证据来自单一维护者的单一仓库。规程本身很重：一次任务要走预飞六步，要 00–07 八件工件和三道闸门，插件任务还有五步闭环，全量 e2e 约 38 分钟（均已验证）。AGENTS.md 里还直接嵌着"用户指令 seq14""被用户指出"这类个人事故记录（已验证）。我读到的材料里，没有任何外部用户、外部仓库或竞品对比的证据（推断：我没做过市场检索） |
| 为什么致命 | ①你自己已经弃用过 speckit 类流程（AGENTS.md 已验证），说明重流程在你自己的场景里都不可持续，目标用户的容忍度只会更低。②规程是事故堆出来的，可移植性未知。③AGENTS.md 本身是通行约定，写规则文件没有壁垒，壁垒只可能在"机器校验加沉淀"。但这个差异点从未被任何外部人验证                                                                                             |
| 默认修正   | 发布对象从"完整 Kit"改为 **Kit-Lite**：5 条以内硬规则、1 个 hook、1 个 CI 工作流、1 个轻量工件模板（`mini-task.md`）。完整九阶段和全部铁律放进"进阶包"，不对外主推。在写 `install.ps1` 之前，先做 3 个外部试用：找 3 位真实开发者，让他们的 Agent 在自己的仓库里装 Kit-Lite 并完成一个小任务                                                                       |
| 验收标准   | 3 个外部试用者中，至少 2 人在 30 分钟内装好并通过一次门禁提交。至少 1 人一周后仍在用。收集的卡点清单 ≥5 条，且每条都已处置为删规则、改规则或保留并写明理由。若 3 人中没有 1 人愿意继续用，则停止"Kit 为主线"的叙事，回到"铸己匣加方法论文档"，不再投入分发层                                                                                                       |

**问题 2：门禁校验"存在性"，不校验"真实性"**

| 项         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 问题       | 现有 pre-commit 只在暂存区触碰 `docs/ai/pilot/` 时才校验，并且只检查八件工件及"关键节"是否齐全（已验证）。纯代码提交不建 pilot 目录就放行（已验证）。Evidence 的 Verified / Inferred / Unknown 是 Agent 自己标的，Review 可以由"另一 Agent"承担（规范已验证），但没有机制保证它真的独立。我上一轮加的 `Pilot:` trailer 和 CI 复跑只解决"绕不绕得过"，仍然只验证存在性。`verify-pilot-artifacts.ps1` 的内部校验深度我没读到（未验证） |
| 为什么致命 | 方法论的核心主张是"可验证、不靠自觉"。同一个 Agent 既写代码又写证据，只要它会填表，门禁就形同虚设。更糟的是，门禁通过会给人"已被验证"的错觉，比没有门禁风险更大                                                                                                                                                                                                                                                                      |
| 默认修正   | 门禁从"存在性"升级到"可复算性"，三层：①**CI 重跑声明的验证命令**，这是唯一不可伪造的证据，工件里的 PASS 只作索引。②Evidence 每条 Verified 必须带命令、退出码和日志路径，CI 比对退出码，对不上直接红。③Review 工件必须记录与 Implement 不同的会话标识；这一项可被伪造，所以只作审计线索，不作拦截依据。同时把"代码文件变更必须带 `Pilot:` trailer"从 warn 提升为 block，并规定无 trailer 的变更集中不得出现业务源码                   |
| 验收标准   | 做一次**伪造演练**：让 Agent 在一个会使测试失败的变更上，写出声称"全部通过"的 Evidence 并提交，CI 必须变红，10 次演练伪造成功 0 次。纯业务代码提交且无 trailer 被拒绝。`--no-verify` 本地提交推送后，CI 变红。人工抽检 5 份历史 Evidence，其命令与退出码都可在 CI 日志中复现                                                                                                                                                         |

**问题 3："Agent 行为评估"名不副实**

| 项         | 内容                                                                                                                                                                                                                                                                                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 问题       | 我给的 10 个 golden case 里，实际是：确定性断言 6 条（Guard 拒绝、路径越界、命令未登记、状态机迁移、掩码、取消后无新步骤）、"known-fail 基线" 3 条（含 case 6 的 MCP 无 token 放行）、阈值待定 1 条。**使用真实模型的是 0 条**。Tier-0 能否注入脚本化模型本身也没验证（未验证）。真正的模型行为评估被推到 Tier-1，"只报不拦"                                     |
| 为什么致命 | 项目自称"AI 原生"。AI 原生与传统软件的本质区别，是输出非确定、提示词会回归、模型升级会改变行为。0 条真实模型 case，一句"这不就是 xUnit 吗"就能击穿定位。另外，把已知缺陷挂成 known-fail 并长期保留，会让红色变成常态，没人再看报告                                                                                                                               |
| 默认修正   | 概念拆开，不再混用：**确定性守卫测试**回归普通测试，不叫 eval。**行为评估**必须用真实模型、多次采样、看通过率。MVP 至少 5 条行为 case，取自台账的真实失败模式（如 006.1 步骤"谎报完成"、009.6 工具定义过多撑爆 prompt）。每条跑 N=5，只记通过率和成本，不拦截主门禁，成本设日预算上限。known-fail 设到期日：到期要么修，要么写成台账"不做"条目，不允许无限期挂账 |
| 验收标准   | 基线报告含 ≥5 条真实模型 case，每条有 5 次采样通过率和 token 或费用。做一次**灵敏度测试**：故意把系统提示词改差，至少 1 条 case 的通过率可见下降，证明评估能感知回归。单次全量运行成本不超过你设定的预算。每个 known-fail 都有到期日和台账引用                                                                                                                   |

**问题 5：公开预览版会带着无认证的对外工具端口**

| 项         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 问题       | 台账 016 记录 MCP 现状为"无 token 放行"，README 又把 MCP 中心作为卖点：对外暴露宿主全部工具（均已验证）。我上一轮的方案是默认 off，再经 shadow 逐步到 enforce，而 D7 又要打预览 tag 公开发布。也就是说，预览版默认仍带着暴露面。另外，安全基线仍写着"内置默认密钥（仅开发默认，生产必须覆盖）"，而架构总览已写"机器派生密钥加密"，两处不一致（已验证），当前实现到底用哪个我没核实（未验证）。MCP 监听地址是否仅限本机，同样未验证 |
| 为什么致命 | 一个以"受控、可审计的 Agent 开发"为卖点的项目，发布物里先有一个可被本机其他进程、甚至局域网调用的万能工具入口，红队一句话就能打穿全部叙事。桌面个人工具的用户多数不会读基线文档去覆盖配置，"默认安全"才算数                                                                                                                                                                                                                        |
| 默认修正   | 把"默认安全"设为**预览发布的硬前置**，而不是后续优化：①MCP 默认拒绝无 token 请求，shadow 观察期缩短为 3 天，之后直接切 enforce，并给老客户端写一行配置的迁移说明。②只绑定本机回环地址。③执行类和写类工具的外部调用需要确认。④首次启动生成随机密钥，禁止使用内置默认密钥加密。⑤安全基线与实现对齐，有差异的以代码为准并更新文档。以上每一项都触碰安全核心，需要你在对应任务的闸门1 明确写"授权"                                     |
| 验收标准   | 全新安装后，不带 token 对 MCP 的工具调用被拒绝。从非本机接口访问被拒绝。执行类工具即使带 token 也需要确认。新装实例的加密密钥与源码中任何常量不同。安全基线文本与上述行为逐条一致。**发布闸**：以上任一项不满足，`v*-preview` tag 不得打                                                                                                                                                                                           |
