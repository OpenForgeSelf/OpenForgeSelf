**一、通用前缀（每个模板使用前先粘贴）**

```text
【通用前缀】
1. 先读 AGENTS.md 与本任务 pilot 目录；读不到的事实标 Unknown，不得猜测。
2. 每条结论标注证据等级：Verified（读过原文或跑过命令）/ Inferred（由事实推出）/ Unknown。
3. 最多问我 3 个问题；其余按最佳假设推进，假设列在输出开头。
4. 禁止发明仓库中不存在的接口、类、路径、配置项。
5. 输出写入 {{落盘路径}}，回复只给：路径、一句话摘要、待我拍板项。
6. 不扩大范围；发现的额外问题只记入 TODO，不顺手处理。
```

**二、10 个提示词模板**

**T1 需求澄清**

```text
【角色】产品负责人兼红队评审，质疑"这件事值不值得做"。
【输入】想法：{{idea}}；目标用户：{{user}}；已知事实与证据路径：{{facts}}。
【输出格式】单个 Markdown，依次为：
1. 假设表（假设｜依据｜等级）
2. 一句话问题陈述（谁、场景、阻碍）
3. 是否需要 AI（结论加不用 AI 的替代方案）
4. 成功判据表（指标｜基线｜目标｜测量方式），≤3 条
5. 非目标 ≥3 条
6. 验收任务表（输入｜期望｜判定方式），3–5 条
7. 风险档（轻量 / 标准 / 重型）及理由
8. 待我拍板（≤3 条，附默认值）
【约束】不写方案，不写代码；没有外部证据的需求必须标 Unknown 并给出验证办法。
【验收标准】每个成功判据可测量；每条验收任务有机器可判的规则；至少 1 条非目标会让我感到"确实要放弃点什么"。
```

**T2 PRD**

```text
【角色】资深产品经理，面向"编码 Agent 会读这份文档来实现"写作。
【输入】T1 输出路径：{{path}}；已有功能文档：{{related}}。
【输出格式】
1. 背景与目标（≤5 行）
2. 用户与场景表（用户｜场景｜当前做法｜痛点）
3. 需求表（ID｜描述｜优先级 P0/P1/P2｜验收条件｜AI 不确定性说明）
4. 人在回路节点表（节点｜触发条件｜谁决定｜超时默认）
5. 非功能（性能、成本上限、安全、可回滚）
6. 范围外、开放问题、指标
【约束】需求用"系统应……"句式，一条一个可验证点；禁止"智能""友好"等不可测词；涉及模型的需求必须写失败时的降级行为。
【验收标准】每条 P0 需求能直接映射到 ≥1 条评估或测试；Agent 读完后能复述范围外清单；无无法判定的形容词。
```

**T3 架构评审**

```text
【角色】首席架构师兼红队，目标是找出最致命的问题，不负责安慰。
【输入】规格或设计路径：{{spec}}；相关 ADR 与"审慎不做"台账：{{decisions}}。
【输出格式】
1. 风险表（风险｜严重度｜触发条件｜证据等级｜修正方案｜修正成本）
2. 与既有不变量冲突清单（条目｜冲突点）
3. 必须先砍的 3 项、必须先补的 3 项
4. 结论：通过 / 有条件通过 / 打回，一句话
【约束】必须覆盖：模型不确定性、成本与延迟、工具权限、数据与记忆污染、可观测性、评估缺口、可回滚性、文档与真源脱节、过度设计；每条风险给出可检验的修正标准；先读台账，不得重复提出已登记"不做"的方案，除非触发条件已满足。
【验收标准】风险按严重度排序且 ≤10 条；每条有可执行修正；至少 1 条指出"方案自己没提到的前提假设"。
```

**T4 工具契约**

```text
【角色】工具接口设计师，目标读者是"模型"和"安全审计"两类。
【输入】工具名：{{name}}；用途：{{purpose}}；所在插件与现有同类工具：{{context}}。
【输出格式】契约表，逐行填写：
名称｜给模型看的描述（≤3 句，写清何时用、何时不用）｜参数表（名、类型、必填、取值约束）｜返回结构｜失败码表｜风险等级（读/写/执行/网络）｜是否需要人工确认｜超时｜幂等性｜审计字段｜正例调用 2 个｜反例调用 2 个
【约束】描述不得与同类工具重叠；写类和执行类必须说明回滚方式；路径与命令类参数必须声明越界处理；不得引入注册表中不存在的依赖。
【验收标准】给定描述，另一模型只凭描述选对工具的正确率可测；至少 3 个越权或畸形输入有明确拒绝码；风险等级与工具分级表一致。
```

**T5 代码生成**

```text
【角色】在既有代码库中工作的工程师，严格遵守 AGENTS.md。
【输入】任务：{{一句话}}；风险档：{{档}}；规格与任务清单路径：{{pilot}}；允许改动范围：{{files}}。
【输出格式】分两步：
第一步（等我批准）：改动文件清单、明确不改什么、验证命令、回滚点、预计风险。
第二步：按文件分块输出改动，每块先写目的，再附对应测试。
【约束】批准前不得改业务代码；一任务一提交；改动文件 ≤5，超出须说明；新功能先在单一真源登记；不引入新依赖，确需引入则写明理由与替代；发现的额外问题只记 TODO。
【验收标准】改动可用一句话描述；每个改动文件在计划中出现过；验证命令的实际输出贴在 Evidence 中；回滚方式已演示一次可行。
```

**T6 测试**

```text
【角色】测试工程师，专门攻击"自述完成"和"模型输出异常"。
【输入】变更说明或 diff：{{change}}；需求验收条件：{{ac}}；仓库既有测试体系：{{test_stack}}。
【输出格式】用例表：ID｜类型（单元/集成/端到端）｜前置｜输入｜期望｜判定规则｜对应需求 ID。末尾列"最可能漏测的 3 个点"。
【约束】只使用项目唯一测试体系，禁止一次性临时脚本；必须包含：正常路径、边界、模型输出为空/超长/格式错、工具失败与超时、越权调用、并发与取消；每个断言要么检查状态要么检查结构，禁止"看起来合理"。
【验收标准】对实现做一次变异验证（故意破坏关键逻辑），至少相关用例变红；每条 P0 需求有 ≥1 条对应用例；用例可在默认命令下重复运行 3 次结果一致。
```

**T7 评估集**

```text
【角色】评估设计师，区分"确定性守卫测试"与"模型行为评估"。
【输入】失败模式来源（台账、日记、事故记录）：{{sources}}；待评对象（Agent 配置、系统提示词、工具集）：{{target}}；成本预算：{{budget}}。
【输出格式】
1. 分类表：每个候选 case 标注属于"守卫测试"还是"行为评估"
2. 行为评估表：ID｜场景｜输入｜判定规则（结构或状态断言）｜采样次数 N｜通过阈值｜来源｜预期状态（pass/known-fail）｜known-fail 到期日
3. 成本估算（单次全量运行）
【约束】行为评估必须使用真实模型且 N≥5；判定只用结构、状态、可计算指标；known-fail 必须有到期日，到期要么修要么登记为"不做"；评估不进默认门禁。
【验收标准】≥5 条行为 case；做一次灵敏度测试——故意把提示词改差，至少 1 条通过率明显下降；全量成本不超预算；每条 case 可追溯到真实来源。
```

**T8 文档**

```text
【角色】技术文档工程师，信条是"代码即真相，文档跟随"。
【输入】变更 diff 或 pilot 目录：{{change}}；目标文档：{{target_doc}}。
【输出格式】
1. 文档正文，开头带 front-matter（功能编号｜状态｜最后更新）
2. 与代码核对表（文档陈述｜代码位置｜一致/不一致）
3. 需同步更新的索引与引用清单
【约束】冲突时以代码为准并在文末写明差异；不新增文档一级目录；不写无法核对的陈述；每个陈述要么能指向代码位置，要么标 Inferred。
【验收标准】核对表无"不一致"未处理项；所有内部链接可达；索引已更新；同一事实在全仓库只有一种说法（给出检索命令及结果）。
```

**T9 复盘**

```text
【角色】复盘教练，直说，不安慰。
【输入】pilot 目录：{{path}}；证据（测试输出、运行记录、耗时）：{{evidence}}。
【输出格式】
1. 结果对目标（指标表）
2. 做对 2 件、做错 3 件
3. 根因分类表（规格｜提示词｜工具｜评估缺口｜执行），每项给证据
4. 下次不再犯的 1 条规则：必须写明由哪个 hook、CI 或测试来卡住
5. 规程税：工件与流程耗时占总耗时的比例
6. 可沉淀资产（类型｜名称｜来源任务）；方法论需修改的具体条款
【约束】没有证据的结论标 Unknown；"提醒自己注意"类规则不算规则，直接作废。
【验收标准】新规则能被机器触发；至少 1 条做错的事指向流程本身而非个人失误；规程税有数字。
```

**T10 路线图**

```text
【角色】产品战略顾问，前瞻但守纪律。
【输入】愿景与原则：{{vision}}；待办与台账：{{todo_and_ledger}}；最近复盘：{{retros}}；资源约束：{{capacity}}。
【输出格式】
1. 阶段表（阶段｜目标｜关键结果｜依赖｜主要风险｜砍线｜进入条件）
2. 本期做、下期做、明确不做三栏
3. 每项的证据来源（待办编号、台账编号、复盘）
4. 需要外部验证的假设及验证办法
【约束】每项必须追溯到证据，凭空想法放"假设"栏；与台账"不做"条目对账，已否决的不得复活，除非触发条件已满足；每期留 ≥20% 容量给规程税与债务。
【验收标准】每期内容在可用容量内可完成；至少 1 项被明确砍掉并写明理由；每个阶段有"完成即可对外证明什么"的一句话。
```
